# Apparent: Agent Instructions

Apparent is the human-to-agent half of a feedback loop: the agent builds, the human looks, points, talks and draws, and the agent understands what was meant and acts. A capture (`⌥⇧S` on macOS or a cabled iPhone with mirror plus native video) records the screen, voice, cursor, clicks and `⇧` ink, and Apparent compiles it into a compact `.apparent` bundle (`contact-sheet.png`, `frames/frame-XX.png`, `summary.md`, `apparent.json`, `recording.mp4` or `recording.mov`, and `audio.wav`) in `~/Library/Application Support/apparent/captures/`. The Mac app is Rust + GPUI with a Swift helper (`apparent-helper`). See README for the iPhone and testing. **Supported platforms are macOS and Linux. Windows is no longer supported:** do not add Windows features, tests, release assets or new documentation. Existing Windows code and historical artifacts are not a support promise; remove them only in a separately scoped change.

## Principles

1. **The human's time is the scarce resource.** Starting (`⌥⇧S`), marking (`⇧`) and handing off (`⌥⇧V` or clipboard paste) should feel instant and take as few steps as possible.
2. **Don't make the agent guess what Apparent can capture.** When the OS, window server, Accessibility tree, browser page or host app knows which window, element, URL or session is on screen, record that fact instead of leaving the agent to infer it from pixels and words like "this part" or "here".
3. **Images stay visual and text carries meaning.** `contact-sheet.png` and `frames/*.png` show the screen, red ink, click ripples and each keyframe's number in a small white corner chip (no `#`, no time), with no rasterized captions or card chrome. `summary.md` and the clipboard carry the time-aligned transcript, interaction events and absolute file paths as plain text that pastes cleanly into a terminal or a GUI composer. Details are in `capture/docs/keyframes-and-text.md`.
4. **Spend the agent's context where the signal is.** Cut keyframes only on real actions, marks or visual changes (never on speech pauses over a static screen), crop to the active region while keeping full frames on disk, and point the agent at `apparent zoom` for a closer look around a moment.
5. **Inspect real bundles when capture output is affected.** For output/UX changes or after Kit tests a capture, inspect the relevant bundles in `~/Library/Application Support/apparent/captures/` (both `summary.md` / `apparent.json` and visual `contact-sheet.png` / `frames/*.png` via `read`). Documentation/tooling-only changes need no capture inspection. For mechanical moves, reuse relevant output evidence after checking source/import/build-input preservation; do not create a new capture solely because files moved. Report unavailable evidence rather than claiming inspection. Proactively surface concrete improvements whenever you spot issues in the output or UX, such as redundant or noisy text in `summary.md`, cluttered or low-density `contact-sheet.png` layouts, unnecessary keyframes (e.g. static frames cut on speech pauses), ghost strokes or misaligned annotations, slow startup or post-processing latency, or clipboard/paste friction.
6. **Make durable app state legible to agents.** Agents cannot reliably infer the current state from a prior conversation, the Settings window, or the running binary alone. Persist every user-controlled setting and feature flag in an inspectable, documented file such as `~/.config/apparent/config.json`; Settings changes must update that file, and file edits must take effect at a documented time (immediately or after restart). Do not introduce a second hidden preference store. Where the OS owns effective state (login registration, permissions, installed links), keep the requested preference in the file where applicable, reconcile it with the OS, and provide a way to check the actual result; a JSON value is not proof that the OS applied it. Preserve unrelated keys and secrets when writing config. Runtime activity such as an active capture is not a preference, but it must be discoverable before an agent changes or restarts the app.
7. **Product features should be shared by default; OS-specific code should only supply the OS mechanics.** Keep user-facing state, behavior and UI in shared Rust/GPUI code; put windowing, input, capture and compositor differences behind platform adapters. Do not gate an entire product feature to one OS because its implementation needs a platform hook. Document any genuine platform limitation in `public/site/src/features.json`, and test the feature's visible behavior on every claimed OS before release; a build or feature-map entry alone does not prove parity.

**Delete verified dead paths instead of refactoring them.** After the strategy merges, bounded coherent cleanup needs no per-deletion approval, including legacy Windows removal (the separately scoped retirement authorization, never new support). First verify requiredness through current consumers, build/runtime/package inputs, supported compatibility/data readers and owner reservations. Remove retired implementations with obsolete tests/references; git history is the archive, not a copied legacy tree. “Not deployed” alone does not prove retirement. Preserve active work, private captures, credentials, evidence and uncommitted files. See `refactor.md` for campaign gates and examples.

**Keep ownership local and changes bounded.** Put behavior in its accountable owner; when touching legacy code, move only the relevant mechanism with its callers/tests, preserve external contracts, and remove donors only after verifying consumers. Coordinate genuine cross-owner contract changes explicitly; ordinary owner-local work must not wait on a central integrator. See `refactor.md` for the current campaign's temporary integration arrangement and canonical architecture boundaries.

## Build, test and install

- Keep `Cargo.toml` and `Cargo.lock` stable. Use `taskpolicy -c utility cargo build -j 3 --offline` and `taskpolicy -c utility cargo test -j 3 --offline -- --test-threads=2` for broad root checkpoints (omit `taskpolicy` on Linux). On Clanker, all new heavy commands and hook-backed pushes run through `/home/simon/.local/bin/t3-build`, once around the outer driver, never nested; the driver honors `T3_BUILD_JOBS`.
- **Proportional verification, not unconditional certification.** `refactor.md` defines the campaign's mechanical/behavior distinction. Mechanical moves require preservation/reconstruction, import/visibility checks, affected compilation on macOS/Linux and focused existing tests. Broad suites belong at integration/shared-build checkpoints, and whenever shared/build/security/lifecycle changes or unknown impact warrant them. New native proof is required for changed native behavior, not merely a moved function. This explicitly supersedes older blanket per-move full-suite/native/bundle-inspection demands; it never converts an unrun check into a pass or waives an unresolved failure. Existing PR gate descriptions must be reconciled against this rule and their actual delta, not silently ignored.
- **Executable routing:** `.githooks/pre-push` and `.github/workflows/verification.yml` use `scripts/verification.py`. Its reviewed document and Engine-test-only rules narrow checks; unknown paths, shared inputs and selector/hook/CI changes broaden to root plus Engine build/tests. It does not guess that an arbitrary Rust diff is mechanical. Until a reviewed focused rule covers a slice, the broad fallback applies. Add a focused rule with deterministic selector tests only when its dependency closure is known. Keep existing website/Connect, updater and release gates; no hook/protection bypass. Feature pushes compare the whole delta from the local `origin/main` merge-base; fetch main before publishing. CI compares the PR base or main push's before-SHA, and missing history broadens.
- **Test changed behavior, not commit IDs.** After a rebase/merge, inspect the delta from the tested candidate, including dependencies and embedded build inputs. Reuse recorded passing evidence for unchanged paths; run focused checks for affected behavior. Do not repeat full suites, native sessions or independent reviews merely because the SHA changed. Broaden verification for shared behavior, conflicts affecting logic, changed build/runtime inputs or uncertain impact; never waive unresolved failures or platform gates. Record what was reused and why, without claiming a fresh run.
- **Follow through on red tests.** When a suite fails, inspect each failure, reproduce it on the affected platform, and fix the underlying code or test contract before reporting completion. Rerun the focused failures and then the full suite on that platform; do not call a filtered pass or an unverified “unrelated” failure green. If access is temporarily unavailable, arrange a bounded waiter and resume the repair. Stop with the exact blocker only when a safe fix cannot be verified; do not loop on speculative patches.
- **Track unrelated problems found during testing or bundle inspection.** First search this repository's open and closed GitHub issues for the symptom and synonyms; read likely matches. Link a matching issue in the handoff instead of creating a duplicate. Only if none matches, create a concise, evidence-backed issue with reproduction steps, observed versus expected behavior, build/commit and platform, and sanitized evidence (label anything not yet reproduced). Keep private captures, recordings, transcripts, credentials and personal data out of public issues and uploads; use a safe synthetic reproduction or describe evidence without publishing private artifacts. Keep the fix outside the current task unless needed to complete it safely; this does not waive the red-test rule above. If GitHub access fails, report the blocker and retain a local draft rather than claiming the search or filing succeeded.
- After changing Rust code, rebuild with `cargo build` before running `target/debug/apparent`: `cargo test` does not rebuild the binary.
- **Linux/Omarchy verification:** A Mac build may not compile on a Linux host (missing Linux platform modules is not a test result). Before calling a Linux-facing Apparent change untestable, load the `scrawl-x1-preview` and `clanker-omarchy-vm-testing` skills, inspect `/home/simon/VMs/scrawl-omarchy/run.sh` and the actual Linux checkout's `AGENTS.md` / `desktop/docs/linux.md`, then build and test the exact candidate in that checkout and exercise it in the isolated Omarchy VM. Check the VM's existing Apparent processes before staging or launching; never replace a worker's app, treat a host build or CLI `--help` as a GUI test, or install to X1 as a substitute for VM verification. Linux has a real GPUI Settings window: open it to check Linux controls, but the installed app proves only its own build, not an uninstalled change. The Mac Swift Settings and cabled mirror still need Mac verification.
- **Delivery contract for assigned implementation:** At the start, identify the intended deliverable (normally a scoped commit and draft PR against current `main`), the required tests/platform proof, and any explicit merge or release request. Carry that target through implementation; do not stop at an uncommitted checkout, a passing local test, or a proposed next step, and do not ask for PR wording approval. Before reporting completion, verify the exact diff, relevant tests, remote branch and PR readback, then give Simon the PR link and honest check state. If verification or access blocks publication, own a bounded resumption where possible; otherwise report the exact blocker and what remains, not “done.” Commit small, coherent, owned changes and push to the task's feature branch before long tests, review, waits or handoff; do not wait for full acceptance. Freeze reviews on committed SHAs. Checkpoints may be incomplete: state remaining checks and keep PRs draft. Never include secrets, private evidence or another writer's changes. A draft PR is not permission to merge, deploy, release, close an issue, or send a message to another person. Merge only when explicitly requested for that work and checks and safety proof pass; if blocked, leave the PR open and report why.
- **"Make it apparent" means show the proof, not just describe it.** Load and run `skills/make-it-apparent/SKILL.md` when Simon uses that phrase. Inspect the complete recording and deliver a playable video in the current conversation where he can access it, with the tested build/platform and limits; a bundle or path on another machine is not a walkthrough. If recording or delivery fails, report the exact blocker and a truthful substitute, without calling the walkthrough done. Do not put private footage in git or publish it without authorization.
- **Experiments:** a change to what users get (the paste, `summary.md`, the images, routing) ships behind an experiment, off by default, until Kit turns it on for everyone. Kit enables one locally with `"experiments": {"<name>": true}` in `~/.config/apparent/config.json`; code asks `shared::handoff::experiment("<name>")` (a value other than true/false, `"yes"`/`"off"` or a number is skipped and logged, and a bad value for any config key drops only that key) (tests see only `shared::handoff::enable_experiment`, never the config file), and `apparent reprocess` / `apparent inspect` take `--experiment <name>` to try one on a bundle. Bug fixes ship normally. Current experiments are listed in `capture/docs/keyframes-and-text.md`.
- **Feature map:** `public/site/src/features.json` lists every user-facing feature with its status (`stable@<version>`, `main`, `experiment:<flag>`, `branch:<name>`, `review:#<pr>`), platforms, shortcuts, config keys and docs. A PR that adds, removes, renames or changes the status of a user-facing feature updates it in the same PR. A release moves its `main` entries to `stable@<version>` (`desktop/docs/release.md`). `cargo test feature_map` fails when a config key or experiment the code reads has no entry, or an entry names one that's gone. The site renders it at the unlinked `/map-tyyxsf5b/` (`MAP_DIR` in `public/site/scripts/feature-audit.ts`), with a status board and what looks inconsistent.
- **Always install and launch via `./desktop/scripts/install-app.sh` (`~/Applications/Apparent.app`)**: Never run `target/debug/apparent` directly as the background daemon because `hivemind clean` purges `target/` directories, which unlinks the binary on disk and causes macOS `tccd` to revoke Screen Recording and Microphone access. `./desktop/scripts/install-app.sh` copies the binary into `~/Applications/Apparent.app`, signs it with Kit's Developer ID (`dev.kitlangton.apparent`) so TCC permissions persist across rebuilds, and restarts the app.
- Agents: `install-app.sh` starts the app with `nohup` from your shell, and the agent's shell tool can kill it when the command returns. If `pgrep -fl Apparent.app` shows nothing afterwards, relaunch with `open -a ~/Applications/Apparent.app`.
- **Installing on another Mac (e.g. from the Studio onto the MacBook Pro):** run `./desktop/scripts/install-app-remote.sh pro`. Running `install-app.sh` over SSH can't sign (no keychain), and running it as a launchd job can't write into the installed app (App Management), so the remote script signs a staging copy in a launchd job and copies it into place over SSH.
  - **Releasing:** follow `desktop/docs/release.md` (version PR, `release-app.sh` with `APPARENT_SPARKLE_DIR`, tag, the Pro's `dev.kit.apparent-appcast` job over `~/.local/share/apparent-release/updates`, appcast PR, site deploy from the Pro, Homebrew PR). Sparkle's tools and the updates folder live under `~/.local/share/apparent-release/`, never `target/` or `/tmp`.

## Safety and recovery

- Never `tccutil reset` Kit's real grants to test permissions (preview the permission panel instead; see `desktop/docs/onboarding-and-settings.md`).
- Test more than one display with a `CGVirtualDisplay` (`desktop/scripts/virtual-display.swift`), never on Kit's desk Mac.
- Never wake or flash Kit's displays: no `caffeinate -d`/`-u`, no real-screen recordings or benchmarks on the Studio (`perf/screen-guard.sh` refuses there). Use the MacBook Pro under `/tmp/pro-gui.lock`, a virtual display or a macvm VM.
- Never play audio out loud on Kit's Macs (`say`, `afplay`, speaker playback) to test the mic or transcription: feed recorded WAVs (`apparent reprocess <bundle> --out … --bench 1 --live-speed 1` streams a bundle's `audio.wav`), use a silent virtual loopback device you remove afterwards, or use the Mac mini VMs (`macvm`).
- Tests never post to a real OpenCode session. Legacy `routing::Hooks` tests keep outside steps isolated.
- **Capture recovery:** Apparent no longer sends captures to OpenCode. Preserve any session metadata in older bundles, but do not treat it as permission to forward anything. Use `apparent copy <bundle>` for clipboard handoff. Ask before any separate outbound delivery to a person, organization, or session.
